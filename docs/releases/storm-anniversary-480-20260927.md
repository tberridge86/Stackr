# Storm Emeralda and 30th anniversary metadata import

The production catalogue contains empty Storm Emeralda and anniversary set shells. This bounded release imports 480 reviewed physical-card printings: Japanese Storm Emeralda (113), English 30th Celebration (161), Japanese 30th Celebration (176), and a separate English Classic Collection (30). It preserves existing production set IDs and creates only the missing Classic set. Pocket is a separate product and release.

TCGdex supplies 450 records; Pokemon TCG API supplies the Classic Collection's 30 factual identities and printed numbers. Frozen raw payloads, source URLs, hashes, provider mappings and source attribution accompany every printing. TCGdex's existing MIT notice remains in THIRD_PARTY_NOTICES.md. This release does not fetch, mirror or publish source artwork, change global source rights or enable recognition training. Unknown provider rarities remain unknown; newly named rarities retain their provider labels.

Classic contains three different cards numbered 106 and two numbered 11. The additive canonical-key contract accepts an optional `:printing:<actual printing UUID>` suffix while preserving every existing key. Printed numbers and finish taxonomy remain unchanged; the existing unique printing/variant and composite identity constraints continue to apply. The 30 Classic records use this explicit identity. Generic imports that cannot resolve such identities must continue to quarantine ambiguous matches rather than guessing. No existing key is rewritten.

Reviewed exceptions include separate paired Stadium numbers 071–076, separate LEGEND halves, the existing Pikachu sequence (not another duplicate subset), RGB Mew identifiers, the eight visually confirmed Japanese energy codes, and the official Mega Gardevoir name for M6a-156. Japanese official gallery omissions do not shrink the source checklist.

The exact frozen cohort uses separate staging and production bindings. Staging contains 242 older Japanese printings and incorrect set totals; the complete rehearsal preserves their identities and rolls back every change. Production begins with zero printings in the three existing shells. Both environments rehearse the one pinned migration plus every metadata/membership write in a serializable transaction before production commits. The migration is recorded with its exact statement in the migration ledger. The lane does not apply other pending migrations. Post-commit verification requires all 480 selected variants in the published catalogue view.

Validation includes frozen-source and identity tests, repeated-number and LEGEND/energy checks, release guards, failure rollback, and an isolated PostgreSQL migration test proving old keys remain valid and mismatched UUID suffixes fail. Full CI and protected production execution remain required. Artwork publication, external HTTP route delivery and installed-device rendering are separate from this metadata receipt.

Rollback must be a separately reviewed forward change scoped to this cohort's version membership and newly inserted identities. Preserve ownership data and any subsequently referenced records. Do not restore the old key constraint while printing-scoped keys exist. Existing artwork releases remain outside this scope.

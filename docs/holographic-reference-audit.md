# Holographic reference audit

This implementation uses no third-party card-effect source or art assets.

The public [pokemon-cards-css](https://github.com/simeydotme/pokemon-cards-css/tree/acb1197633e749a1fba4412231db2f6581586d00) repository is GPL-3.0 under its [pinned licence](https://github.com/simeydotme/pokemon-cards-css/blob/acb1197633e749a1fba4412231db2f6581586d00/LICENSE), and its README credits additional third-party background material. Its code and textures are excluded. [Pokebox](https://github.com/selop/pokebox/tree/7f6b1b4b6bb4684f80b49d1318b2a1c90a357b80) is MIT under its [pinned licence](https://github.com/selop/pokebox/blob/7f6b1b4b6bb4684f80b49d1318b2a1c90a357b80/LICENSE), but its README identifies Pokémon/card data and an effect lineage outside its licence; its GLSL and assets are excluded. [TiltHologramCard](https://github.com/DongGukMon/TiltHologramCard/tree/d18fa0600e820c84569d7a348b0afdd8b971ce2a) had no repository licence at the pinned audit revision, so its code and assets are excluded.

## Reference findings

Browser review covered the Simey live demo, Pokebox’s room/modal without enabling its camera, and TiltHologramCard’s `hologram_light_mask` demonstration GIF. These observations informed interaction expectations only; they are not device-performance or rendering-parity evidence.

- Simey’s [card interaction component](https://github.com/simeydotme/pokemon-cards-css/blob/acb1197633e749a1fba4412231db2f6581586d00/src/lib/components/Card.svelte) separates rotation, glare, and background position, batches pointer updates with an animation frame, and exposes those values as CSS variables. Its [base composition](https://github.com/simeydotme/pokemon-cards-css/blob/acb1197633e749a1fba4412231db2f6581586d00/public/css/cards/base.css) uses separate transformed layers and a clipped card surface. Its rarity-specific files demonstrate the general visual structure of masked foil, patterned layers, and pointer-centred glare: [regular](https://github.com/simeydotme/pokemon-cards-css/blob/acb1197633e749a1fba4412231db2f6581586d00/public/css/cards/regular-holo.css), [rainbow](https://github.com/simeydotme/pokemon-cards-css/blob/acb1197633e749a1fba4412231db2f6581586d00/public/css/cards/rainbow-holo.css), and [cosmos](https://github.com/simeydotme/pokemon-cards-css/blob/acb1197633e749a1fba4412231db2f6581586d00/public/css/cards/cosmos-holo.css). Stackr independently implements only those broad ideas: finish selection, geometry-limited coverage, and hand-driven glare.

- Pokebox’s [architecture](https://github.com/selop/pokebox/blob/7f6b1b4b6bb4684f80b49d1318b2a1c90a357b80/docs/architecture.md) separates static card textures, finish-specific shaders, input sources, and frame-updated uniforms. Its [uniform registry](https://github.com/selop/pokebox/blob/7f6b1b4b6bb4684f80b49d1318b2a1c90a357b80/src/data/shaderRegistry.ts) supports a single configuration-to-material mapping, while its [per-frame updater](https://github.com/selop/pokebox/blob/7f6b1b4b6bb4684f80b49d1318b2a1c90a357b80/src/three/ShaderUniformUpdater.ts) keeps light coordinates dynamic. Its renderer caps device pixel ratio at two in [scene setup](https://github.com/selop/pokebox/blob/7f6b1b4b6bb4684f80b49d1318b2a1c90a357b80/src/composables/useThreeScene.ts). Stackr’s original material similarly keeps motion as input to a bounded procedural response, but does not port Pokebox’s GLSL, texture pipeline, camera model, or scene composition.

- TiltHologramCard’s [component](https://github.com/DongGukMon/TiltHologramCard/blob/d18fa0600e820c84569d7a348b0afdd8b971ce2a/src/components/TiltCard.tsx) combines gyro-derived card rotation, a derived moving gradient, and luminance masking on a Skia/Reanimated stack. Stackr uses its own sensor calibration and its own procedural SkSL; the reference supports the design choice to keep sensor values bounded and let light follow input, not a claim of implementation or native-device parity.

The Stackr source and CPU/WASM shader swatches were compared qualitatively. Native-device rendering parity, frame-time, battery, and GPU measurements remain pending and are not established by the browser review or CPU/WASM output.

`lib/cardHoloProfile.ts` therefore resolves only Stackr canonical variant facts. It reads the legacy adapter's `raw_data.language` (or direct API `stackr.languageCode`), with an optional viewer language only for a payload that contains neither. It does not infer a finish from the card name, rarity, condition, image, provider, or selected label. Unknown, malformed, and stale selections return a visually plain result.

Mask records are local metadata, not network URLs. A mask must match the canonical card (the Stackr printing identity), language, and selected variant. A valid printing-specific record wins over a template record. Geometry must be finite, inside normalized card bounds, non-empty, and contain no more than four regions. Missing or rejected masks disable colour for cosmos, reverse, and diagonal effects while retaining only a neutral reflection. Only explicitly textured or radiant canonical finishes can use the restrained full-card generic fallback until a verified art-window mask is available. Generic `holo` is represented as diagonal geometry but stays neutral until a registry entry verifies its material area.

`lib/cardHoloMaskRegistry.ts` exports an intentionally empty verified registry. The tracked SQLite catalogue pack is explicitly blocked pending curated catalogue metadata, so it is not evidence for a real printing/layout record. No verified record was invented. `data/fixtures/card-holo-profile.synthetic.json` contains seven explicitly synthetic geometry-only cases for renderer tests and makes no catalogue claim.

The six profiles are original parameter presets for a Stackr renderer: `plain`, `cosmos`, `reverse`, `diagonal`, `textured`, and `radiant`. They are not implementations or ports of the cited projects.
